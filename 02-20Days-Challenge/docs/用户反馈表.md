# 用户使用反馈表（8 位真实用户）

对应评审第 ③ 项（15 分）中的"8 位真实用户使用反馈"。
关键不是凑够 8 个人，而是**每个人的反馈能被追溯到具体日期和具体功能**。

## 一、收集原则（这三条不做，反馈会被当成编的）

1. **必须是真用过的人**：每人至少连续用 3 天，且能在对方的聊天记录/朋友圈/截图中找到痕迹。
2. **不问诱导性问题**：不要问"是不是很方便？"，要问"哪一步让你想放弃？"
3. **保留原始证据**：每人的反馈截图存 `docs/feedback/u01.png` … `u08.png`（打码手机号）。

## 二、8 位用户的建议构成

| 编号 | 建议身份 | 为什么选他 | 能暴露什么问题 |
| --- | --- | --- | --- |
| U01 | 班长 / 团支书 | 天天转发通知，是通知的源头 | 转发的通知格式最乱，最能压测抽取规则 |
| U02 | 社团负责人 | 要统计报名、催截止 | 截止时间与报名统计是刚需 |
| U03 | 同班同学（普通） | 只关心"今天要干什么" | 日报可读性 |
| U04 | 室友 | 常常漏看群消息 | 漏通知的真实痛点程度 |
| U05 | 实验室 / 实训室同学 | 有借还器材、补课通知 | 地点与携带物品字段 |
| U06 | 高年级学长 | 面试/竞赛通知多 | 长期使用意愿 |
| U07 | 学生助理 / 辅导员助理 | 一天几十条通知 | 批量处理的性能与去重 |
| U08 | 完全不关心技术的同学 | 最能代表"零门槛"要求 | 安装与上手成本 |

## 三、每人记录什么（照这张表问，别自由发挥）

| 字段 | 说明 |
| --- | --- |
| 使用天数 | 从哪天到哪天，对应 `process_logs/` 里的日期 |
| 每天大概用几次 | 与日志里的 `calls` 交叉验证 |
| 解决了他什么问题 | 具体到某一条通知 |
| 哪一步卡住了 | 必须写出具体动作，如"不会解压 zip" |
| 有没有继续用的意愿 | 1–5 分 |
| 原话引用 | 一句原话，比评分更有说服力 |

## 四、访谈提纲（8 问，按顺序问）

1. 你平时最容易被哪类通知坑到？（漏看 / 看漏时间 / 不知道要带什么）
2. 最近一周，有没有因为漏看通知而吃亏的事？具体说说。
3. 我做的这个东西，你第一次打开时知道该干什么吗？
4. 哪一步让你觉得麻烦，甚至想放弃？
5. 日报里有没有你根本不需要的信息？
6. 如果它明天开始收费 1 块钱，你还会用吗？为什么？
7. 你更希望它出现在哪里？（微信 / 日历 / 桌面小组件）
8. 你会推荐给谁？为什么不是所有人？

> 第 6 问是"真实意愿"的试金石，第 8 问能问出产品的真实边界。

## 六、反馈如何反哺迭代（这一步是加分项）

汇总后按"被提到次数"排序，写进 `02-20Days-Challenge/iterations/iteration-plan.md`：

- 提到 ≥3 次的卡点 → 优先在下一版修，并在 commit message 里引用"U03/U05/U07 反馈"
- 只有 1 人提到的 → 记进 README 的"已知局限"，不急着做

这样能证明：**功能优先级是用户反馈决定的，不是我拍脑袋决定的。**

## 七、隐私处理

- 反馈截图里对方姓名、头像、手机号需打码；
- 反馈表中用 U01–U08 编号，不写真实姓名；
- 若对方不愿公开，注明"已口头授权，匿名收录"。
