# 时间不够了怎么办（11-20 起步的实话）

## 结论先说

**7 天从今天起算，最早 11-26 完成，比大纲的 11-24 晚两天。这个缺口补不了。**
下面三条路都能走，按推荐排序；第 4 节写了为什么"补日志"这条路走不通。

---

## 1. 为什么补日志一定会露

不是道德问题，是技术上藏不住。评审只要做三件事：

```bash
# ① 提交时间：7 个文件是不是逐日提交的
git log --format="%ad %s" --date=iso -- 02-20Days-Challenge/process_logs/

# ② 日志内部时间戳与文件修改时间是否吻合
ls -l --time-style=full-iso 02-20Days-Challenge/process_logs/

# ③ 日期分布是否"太整齐"
python run.py digest
```

真实的 7 天日志一定有波动：周末通知少、某天 `notices` 为 0、
某天耗时突然飙到 300ms。补出来的日志往往每天条数几乎一样、耗时平滑，
`digest` 的"断档/连续性"那一节一眼就能看出不自然。

更硬的约束在第三阶段面试（占 20 分）：**"调取 Commit 历史，追问采样边界、
异常数据原因及排障细节"**。编出来的那天没有对应的真实通知、没有当时的报错、
没有改代码的动机，第一个追问就答不上。

## 3. 方案 B：5 天 × 3 次 = 15 次运行（硬截止 11-24）

把"天数不够"换成"密度来补"，这是唯一能在 11-24 前拿出的真实数据。

### 怎么跑

定时任务已经改成一天三个时段（早/午/晚各抓一次不同批次的通知）：

```powershell
powershell -ExecutionPolicy Bypass -File 02-20Days-Challenge/tools/register_task.ps1 -StartNow
```

`-StartNow` 会立刻触发一次，今天就有第一条日志。

### 三个时段分别投什么

| 时段 | 投什么通知 | 日志会体现什么 |
| --- | --- | --- |
| 08:00 | 昨晚到今早的群消息 | 隔夜通知批量处理，`notices` 偏多 |
| 12:30 | 上午的课务/社团通知 | 单条居多，耗时稳定 |
| 21:30 | 全天补漏 + 明天安排 | 去重率高（前两次已入库的会重复） |

三个时段处理的内容不同，`notices` / `dedup` / `dur_ms` 自然有差异，
不需要人为制造波动。

### 能拿到什么

11-20 到 11-24：**5 个日志文件、15 次运行、约 250~350 条事件记录**。
横向对比同批同学，这个数据量不算少——缺的只是"天数"这一个指标。

### README 里怎么写（诚实模板，直接改数字）

```markdown
## 关于日志天数的说明

本项目自 11-20 开始运行，至 11-24 提交时共 5 天、15 次定时运行
（每日 08:00 / 12:30 / 21:30）。受开发完成时间限制，未能凑满 7 天；
第 6、7 天日志将于 11-26 追加提交于 process_logs/。

为弥补天数不足，我把采样频率提高到每天 3 次，日志覆盖了早/午/晚
三个通知高峰，事件总量与 7 天单次运行（约 7×18=126 条）相当甚至更多。
```

这段话本身就是加分项：**说明你清楚要求、量化了差距、给出了补偿措施**，
比含糊带过强得多。
