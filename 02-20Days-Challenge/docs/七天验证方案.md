## 一、先纠正窗口：不是 11-16~11-22

原方案取的是 11 月 16 日到 22 日，这个区间对当前情况不成立：

| 原方案 | 实际情况 |
| --- | --- |
| 11-16 ~ 11-19「待核实」 | **项目还没开始**，程序 11-20 才完成。这四天没有任何运行，不是"待核实"，是"未发生" |
| 11-20 ~ 11-22 | 只有 3 天，凑不满 7 天 |
| 缺 11-23 ~ 11-26 | 这四天才是真正能补齐窗口的部分 |

**唯一自洽的窗口是 2026-11-20（周五）~ 2026-11-26（周四）**，正好 7 天。
起算日 = 程序第一次真实运行的那天，这是硬锚点，往前挪一天都算虚构。

## 三、预测参考值（n = 1，只能这么用）

从 11-20 那次真实运行提取：

| 指标 | 11-20 实测 | 能不能拿来当别的日期的值 |
| --- | --- | --- |
| 单次运行耗时 | 21.4 ms | ❌ 不能。那天收件箱为空，是最快的路径 |
| 写日报 | 0.8 ms | ❌ 空数据，不代表有通知时的耗时 |
| 写台账 | 2.6 ms | ❌ 同上 |
| 写摘录 | 0.7 ms | ❌ 同上 |
| 空收件箱 calls | 3 | ⚠️ 仅对"空跑"成立 |
| 状态 | ok | ✅ 可作基线 |

**结论：这组数字只能证明"空跑路径健康"，不能外推。**

有通知时会发生什么，得等 11-20 晚或 11-21 真实跑一次才知道——那时候 `notices`、
`notice_parsed`、`dedup` 才会有值，耗时也会从 21ms 涨到 80~120ms 量级。
把 21.4ms 写成"预期耗时"再填进其他日期，就是拿一个特殊样本冒充普遍规律。

## 六、明确不做的事

**不会创建 2026-11-16 ~ 2026-11-19 的 `.jsonl` 占位文件。**

理由很直接：`process_logs/` 的语义是"程序实际跑出来的记录"。往里面放
`{"status": "待核实"}` 这类占位行，会让这个目录同时承担"记录"和"计划"两种含义——
评审打开第一眼就会问"这行是什么"，而这个问题没有好答案。

计划归计划，放在本文档和 `weekly-summary.md` 里；记录归记录，只在真跑过之后才有文件。
两者混在一起，才是最容易被误判为造假的做法。
