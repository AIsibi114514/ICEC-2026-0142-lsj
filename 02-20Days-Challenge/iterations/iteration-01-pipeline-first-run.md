## 触发问题

第一版只有 `python run.py all` 一条路。跑一次 114 秒，中途任何一步出错（读音频、提特征、训练、出图），打出来的只有一句 `Traceback`，得从头再来一遍。

更麻烦的是**它掩盖了"哪一步真的在起作用"**：全流程一次成功，看上去很顺，但我并不知道 `blind_seal` 封装和 `blind_predict` 预测之间的边界是不是真的隔离了——因为从来没单独跑过其中任何一步。

## 改了什么

把流水线拆成 9 个可独立执行的子命令，每个子命令自己开一次 `Telemetry`、自己落一条 `run_end`：

```
index → features → train → blind_seal → blind_predict → blind_score → blind_verify
      → noise → confidence → stress → baseline → export_csv → figures
```

拆分后立刻暴露了两件事：

1. **`blind_seal` 与 `blind_predict` 必须分属两次运行**，否则"预测阶段不接触标签"只是代码注释里的一句话，没有任何外部证据。拆开之后，`blind_seal` 的 `key_sha256` 落在 12:33:36、`blind_predict` 落在 12:33:37——两条记录之间的模型文件只有 `model_blind.json`，这就是隔离的物证。
2. **抗噪那一轮（`noise`，39 组条件）要跑 55 秒**，占全流程一半时间。之前混在 `all` 里，每次改特征都要重跑 55 秒；拆开后调特征只跑 `features && train`，约 7 秒（0.9 s + 6.0 s），当天下午的试跑次数从个位数变成了 28 次。

## 结果

同一天留下了 28 次运行、88 条事件，其中 3 次是完整 `all`（`cfa7365a` 12:58、`c7b4a720` 13:07、`c7756cc6` 14:16）。前两次的产物被第三次覆盖了，但运行记录还在——**这正是日志该干的事：结果可以被覆盖，过程不该被覆盖。**

抗噪那一项的演进也留在了日志里，这是拆分之后才好观察的：

| 时间 | run_id | 抗噪条件数 |
| --- | --- | --- |
| 12:42 | `02333ba5` | 24 |
| 12:43 | `7cdb314a` | 26 |
| 12:45 | `1c4a9726` | **39**（此后再没减过） |

从 24 组到 39 组，中间隔了三次运行、约 2 分钟。**日志只记了"条件数变了"，没记"为什么变"**——这是我当时留痕的疏漏：`telemetry.log` 允许带任意字段，我完全可以写一行 `reason="补中间档"`。下次这类调参必须把动机一起落盘，否则事后只能重建，不能追溯。

## 反思

拆分流水线的收益不是"更快"，是**让每个中间状态都变成可检查的对象**。如果只交 `all` 的一次输出，我能证明的只有"最后跑通了"；拆开之后我能证明"盲测封装发生在预测之前""抗噪跑了几轮""哪一轮改了参数"。

反过来说，这也是这次交付最弱的地方：**28 次运行全部集中在一天**。拆分带来的高频试跑，反而让"20 天做了多少事"这个问题更难回避——真实答案就是"方案定了两天、实现压到最后一天"。我在根 README 的缺口表里如实写了这一点，没有用补录日志去粉饰。
