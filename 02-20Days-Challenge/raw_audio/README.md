# raw_audio/ —— 75 段录音的口径说明

## 一、为什么 75 个文件的大小完全一样

75 个 WAV **全部是 48000 帧 / 16 kHz / 16-bit / 单声道 = 精确 3.000 秒**，字节数都是 96 044（44 字节头 + 96 000 字节数据）。

这不是巧合，也不是事后拼接，是**采集口径**：

- 每段设计录制 **3.0 s**（高档轴频约 36 Hz / 2170 r·min⁻¹，3 s 覆盖 100 转以上；BPF≈181 Hz，2 s 分析窗内仍有 300+ 个周期，频谱分辨率 0.5 Hz 足够把 BPF 与次谐波分开）；
- 导出统一为 **16 kHz / 16-bit / 单声道**（16 kHz 的奈奎斯特上限 8 kHz，覆盖擦碰指纹所在的 2–8 kHz 频段；再高只是涨体积）。

分析时**去头去尾各 0.5 s，只用中间 2.0 s**（`trimmed_seconds: 2.0`，见 `../sample_index.csv` 与 `../results/`）。头尾各 0.5 s 是为了避开手按录音键、放下手机带来的操作冲击。

> 所以：**磁盘上的 3.000 s 是录制长度，报告里所有指标基于的是中间 2.0 s 的分析窗。** 两者不要混。

## 二、这批文件就是最初的那一份（已与本地存档逐字节核对）

初版这一节写的是「为分析统一过的版本，原始容器未入库」——**这个说法是错的，已更正。**

11-25 把本地存档（`新建文件夹.zip`，8.87 MB，内含 76 个 wav）与仓库逐字节比对：

```
与仓库逐字节一致: 75    不一致: 0
```

即：**仓库里的 75 段就是最初导出的那一份，没有重采样、没有二次裁剪。** 3.000 s / 16 kHz 是录制口径本身产出的形态（固定 3 秒录音、导出单选 16 kHz 单声道 PCM），不是事后加工的痕迹。

| 项 | 本目录 / 本地存档 |
| --- | --- |
| 容器 | `.wav`（PCM 未压缩），无 `.m4a` 中间格式 |
| 采样率 | 16 kHz |
| 声道 | 单声道 |
| 时长 | 每段 3.000 s（录制时长设定值） |
| 时间戳 | 存档内 75 个文件 mtime 统一为 **2026-11-23 16:28** |

顺带纠正一处日期错误：初版 README 与本仓库若干处把录音写成 11-24，**实际采集时间是 11-23 16:28**（存档时间戳可查），11-24 是分析、迭代与提交那一天。这个差别有意义——它说明项目**至少跨了两天**（11-23 采集 / 11-24 分析），而不是"一天做完"。但两天不等于大纲要求的"连续多日"，缺口照旧记在根 README。

**核对方法**（任何人可重跑）：

## 二点五、存档里那个 `ALL_75_samples.wav` 不能用来做分析

本地存档还带一个合集文件 `ALL_75_samples.wav`（**8 kHz / 120 s**），是把 75 段拼起来方便试听的。

**它的采样率被降到了 8 kHz，奈奎斯特上限只有 4 kHz**——而 C5（网罩擦碰）的指纹在 **4–8 kHz**。用它试听可以，用它论证"C5 靠高频指纹可分"会把证据本身切掉。

同理，任何把音频转发进微信再取回的操作都会重采样到 8 kHz 或更低。**原始文件只在本地存档和 `raw_audio/` 里，别经聊天软件转。**

## 四、完整性自校验

每段录音的 `sha256` 前 16 位登记在 [`../sample_index.csv`](../sample_index.csv) 的 `sha256_16` 列，文件被改动过会立刻对不上：

```bash
cd 02-20Days-Challenge
python -c "
import csv,hashlib,pathlib
bad=0
for r in csv.DictReader(open('sample_index.csv',encoding='utf-8')):
    p=pathlib.Path('raw_audio')/r['file']
    h=hashlib.sha256(p.read_bytes()).hexdigest()[:16]
    if h!=r['sha256_16']: print('MISMATCH',p.name); bad+=1
print('核对',75,'段，异常',bad,'段')
"
```
