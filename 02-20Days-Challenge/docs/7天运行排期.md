## 每天固定 3 分钟流程（定时任务已一天跑三次，你只管投料）

```bash
# 1. 把今天的通知复制进 inbox/，文件名用日期
#    inbox/2026-11-21.txt
#    分三批投更好：早上投一次、中午追加、晚上再补 —— 三次运行的 notices 数就会不同

# 2. 手动补跑一次（定时任务也会跑，手动跑是确认当天有数据）
cd 02-20Days-Challenge && python run.py run

# 3. 看日报，确认抽得对不对（不对就记下来，这是迭代素材）
cat output/2026-11-21.md

# 4. 提交
cd ../.. && git add -A && git commit -m "logs: 11-21 运行日志" && git push
```

> 关键：**每天都要 commit 一次日志**。评审看的是 `git log -- process_logs/` 的时间线，
> 如果 7 个日志文件在同一次 commit 里出现，前面的努力会被直接判为不可信。

## 给 8 位用户怎么用最省事

```bash
python 02-20Days-Challenge/run.py web
# 或者直接双击仓库根目录的「网页.bat」
```

打开后他们只需要：粘贴群通知 → 点「解析通知」→ 看原文高亮和右边字段 → 点「加入今日待办」。

- 默认只监听 `127.0.0.1`，别人访问不到，只有你自己能用；
- 想让同宿舍 / 同实验室的人用自己的手机或电脑用：加 `--host 0.0.0.0`，然后让他们打开
  `http://你的内网IP:8765/`（查 IP：`ipconfig`）。**只在可信的校园网/宿舍网里开**，
  不要映射到公网，因为里面是同学的真实通知内容。
- 他们的每次解析都会写一条 `web_extract` 到 `process_logs/`。
  跑 `python run.py digest`，报告第 5 节会按天列出「网页解析次数」——
  这是"8 位真实用户真的用了"最硬的证据，比一张聊天截图强得多。

## 每天应该"故意"制造一点真实波动

完全相同的日志反而可疑。真实使用自然会带来这些：

- 周末通知少 → `notices` 数下降，甚至某天为 0（空跑 + `warning`，这是加分的真实感）
- 某天群通知格式特别乱 → `confidence` 掉到 0.4，正好是 v0.3.0 的依据
- 截图识别失败 → `error` 事件，正好是 v0.2.0 的依据

不要为了好看去修改 JSONL。日志有瑕疵但能解释，比完美但无从解释强。
