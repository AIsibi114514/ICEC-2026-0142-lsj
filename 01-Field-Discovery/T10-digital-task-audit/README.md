# 课题 10 · 日常数字任务耗时审计与 AI 批处理实证

> 第一阶段实地测评 · 10 选 2 之一
> 原始要求：记录一项高频重复性数字任务（表格汇总、文件重命名、笔记提取等），对比人工与 AI 脚本/工作流处理 10 个样本的耗时；交付任务样本、AI 脚本/Prompt 与耗时对比表，制定人机校验规则。

**本课题选定的任务**：把散落在微信群、教务系统、公众号里的**课程通知原文**，整理成一张字段统一的**课程安排表**。

---

## 0. 为什么选这个任务

选任务不能选"看起来技术含量高"的，要选**真的每周都在做、做了会烦、烦了会错**的。这个任务满足三条：

1. **高频**：一个学期至少几十条调课/讲座/补考通知，每条都要手动抄进日历或备忘录。
2. **有明确正确答案**：日期、时间、地点都是客观事实，对错可判定——这让"准确率"能变成可量化的指标，而不是主观感受。
3. **痛点真实**：抄错的代价是跑错教室。而且通知的表述千奇百怪（"下周三""第12周周二""明天"），人也会抄错。

**这个任务的核心矛盾不是"快不快"，而是"信息形态的转换"**——从自由文本变成结构化字段。凡是这种转换，AI 都有结构性优势；而这类转换恰好占了学生日常数字劳动的一大半。

## 1. 样本设计：10 份通知，每份埋一个坑

样本在 `samples/N01.txt ~ N10.txt`，由 `samples/_make_samples.py` 生成（可复现）。**每份都对应一种真实存在的表达难点**，这是刻意设计的——如果 10 份都是格式规整的教务公文，测出来的耗时不具备代表性。

| 样本 | 埋的坑 | 人工容易错在哪 |
| --- | --- | --- |
| N01 | 典型教务公文；一条通知里有两个日期、两个节次（原定 vs 调整后） | 抄成原定的 11月19日 / 第5-6节 |
| N02 | 微信群消息，@所有人 + emoji + 感叹号；只写"明天"；地点从"信405"改到"426实践工坊" | 抄成旧地点；或不知"明天"是哪天 |
| N03 | 相对时间"下周三""下午两点到三点四十""下周五晚上12点前" | 时区/上下午算错；漏掉截止时间 |
| N04 | 教学周表达"第12周周二（3-4节）" | 不会换算成具体日期；节次不会转钟点 |
| N05 | 一条消息 4 个课程事件 | 只抄了第一条，漏掉其余三条 |
| N06 | "14:00—15:40"破折号范围 + "同一时间段"指代 + 地点括注"（426工坊旁）" | 把括注当成地点 |
| N07 | 语音转写稿：口语、停顿、"这个礼拜五""下午三点" | 找不到关键信息；漏掉截止时间 |
| N08 | 补考通知，"具体时间另行通知"这类不可解析值 | 硬填一个日期，反而制造了假信息 |
| N09 | 闲聊中夹带通知，且没有课程名（实为班会） | 整条漏掉 |
| N10 | 公众号推文，标题党；活动时间与"报名截止"时间混在一起 | 把截止日期当成活动日期 |

**基准锚点**：`2026-11-12`（周四）。所有相对时间（明天、下周三）都以它为基准解析；教学周以 `2026-09-07` 为第 1 周周一。这两个值在 `scripts/ai_extract.py` 顶部可改。

## 2. 字段口径（这就是"人机校验规则"的源头）

**必须先定义口径，再比较耗时。** 否则人工和 AI 填的不是同一张表，比出来的耗时毫无意义。这是本课题最容易被忽略、却最影响结论可信度的一步。

| 字段 | 口径 | 校验要点 |
| --- | --- | --- |
| `course` | 课程名，以《》内为准；无书名号时取校内课程全称 | 不能是简称（"通信原理"≠"通信"） |
| `date_iso` | 事件**生效**那天的日期，`YYYY-MM-DD` | 调课场景必须取**调整后**的日期 |
| `time_start` / `time_end` | 24 小时制 `HH:MM`；节次按作息表换算；无结束时间则留空 | 留空 ≠ 填 00:00 |
| `location` | 楼名+房间号，去空格、字母大写；括注内容不算地点 | "教学楼441（426工坊旁）"→`教学楼441` |
| `deadline` | 提交/报名截止；有明确时刻则附 `HH:MM` | 不能用活动时间充当截止时间 |
| `action` | 停课 / 补考 / 考试 / 讲座 / 会议 / 调课 / 上课 / 未识别 | 一条通知多个动作时取主要动作 |

> **留空原则**：原文没写的信息，一律留空，**绝不允许 AI 或人"猜一个填进去"**。N08 的"具体时间另行通知"在 `deadline` 字段就必须留空。这条规则是后面第 5 节"人机校验"的第一条铁律。

## 3. 人工计时协议（必须自己动手，这是数据来源）

**你要亲手把 10 份通知手工整理进一张空表，并用秒表计时。** 这一步不能由 AI 代劳——否则这个课题就变成了"AI 说我很快"，没有对照就没有结论。

### 3.1 工具
- 秒表：手机自带即可，或用 `vclock.net`（网页秒表，可分段计时）。
- 表格：Excel / WPS 新建一个空表，表头就用第 2 节的 7 个英文字段名。

### 3.2 流程（逐样本，共 3 轮）

```
① 秒表归零，手指放在开始键上
② 打开 samples/N01.txt，开始计时
③ 阅读通知 → 在表格里填 7 个字段
④ 填完最后一个字段，立刻停表
⑤ 把秒数记进 manual_run/timing_sheet.csv 的 manual_round1_s
⑥ 核对一遍（对照 ground truth），把填错的字段数记进 manual_err_fields
⑦ 下一个样本
```

### 3.3 为什么必须做 3 轮

这不是重复劳动，而是在测**熟练度效应**：

- **第 1 轮**：边看边想口径，最慢，通常比第 3 轮慢 1.5–2 倍。
- **第 2 轮**：开始有套路。
- **第 3 轮**：进入稳定产能，**这一轮才是你真实的长期效率**。

取舍用**中位数**（第 2 轮的值往往是中位数），不用平均数——平均数会被第 1 轮的学习成本拉偏。

> ⚠️ **诚实要求**：3 轮之间不要"记答案"。如果第 2 轮你直接照着第 1 轮的表抄，测出来的就不是"处理耗时"而是"抄写耗时"，数据作废。正确做法是：每轮都从空白表开始，重新读原文。若嫌麻烦，至少隔一天再跑第 2、3 轮。

### 3.4 填表格式

`manual_run/timing_sheet.csv`：

| 列 | 填什么 |
| --- | --- |
| `sample_id` | `N01` … `N10` |
| `manual_round1_s` / `2_s` / `3_s` | 三轮秒数（纯数字，单位秒，可带小数） |
| `manual_median_s` | 可留空，脚本不读这列，只用于你自查 |
| `manual_err_fields` | 该样本你填错的字段数（0–7） |
| `ai_check_s` | 第 5 节"AI 结果校验"的耗时（秒） |
| `note` | 异常说明，如"第2轮被打断" |

### 3.5 一次性成本也要记

`manual_run/audit_config.csv` 里两个值，**必须如实填**，否则摊销曲线算不出来：

- `ai_build_minutes`：你和 AI 一起把脚本调到能跑通，实际花了多少分钟（含提问、改错、跑不通再问的往返）。
- `manual_setup_minutes`：人工这一侧的一次性准备时间（建表头、想清楚字段口径）。

> **这两个数字是整份报告最有价值的地方。** AI 的单次运行只要 2 毫秒，但它有构建成本；人工单次很慢，但几乎没有构建成本。**只有在第几次使用之后 AI 才真正开始省时间——这才是"AI 提效"这句话的准确含义。** 敢把这个数字填出来的人，才是在做审计；只说"AI 快 4 万倍"的人，是在做广告。

## 4. AI 流水线

`scripts/ai_extract.py`：一条纯本地规则流水线，不调用任何在线大模型。

**为什么不用 API 调大模型？** 三个理由：

1. **耗时不可控**：网络抖动、限流、排队会让"耗时"变成随机变量，审计结论失去意义。本地流水线的耗时是确定性的、可复现的。
2. **隐私**：课程通知里有课表、教室、教师信息，不必上传。
3. **可解释**：规则出错时能定位到具体哪条正则，模型出错时只能重试。

这不是说规则优于模型——**在本任务的字段抽取场景下**，日期/时间/地点都是强模式信息，规则足够且更稳。换成"总结通知要点""判断通知紧急程度"这类任务，就必须上模型了。**知道什么任务该用什么工具，比会用工具更重要。**

### 4.1 运行

```bash
cd T10-digital-task-audit
python -m pip install -r scripts/requirements.txt   # 仅需标准库，此行可跳过

python scripts/ai_extract.py                  # 看提取结果
python scripts/run_benchmark.py --repeat 50   # 计时 + 准确率评估 + 出图
```

### 4.2 流水线结构

```
samples/N*.txt
   ↓ normalize()        全角→半角、礼拜→周、至→到
   ↓ strip_deadline_clauses()   剥掉"报名截止"句，避免污染主事件
   ↓ split_events()     按 1./2./3. 编号拆多事件
   ↓ 逐事件：
       ├ resolve_date()      绝对日期 / 教学周 / 相对周 / 明天
       ├ resolve_time()      HH:MM 区间 / 中文时段 / 单个时刻 / 节次换算
       ├ resolve_location()  楼名+房号，清括注，取最后一个（改地点场景）
       ├ resolve_course()    《》优先，课程词典兜底
       ├ resolve_action()    关键词优先级：停课>补考>考试>讲座>会议>调课>上课
       └ resolve_deadline()  "截止/前交"窗口内取日期
   ↓ 合并 → raw_data/ai_extracted.csv
```

### 4.3 三个被真实样本逼出来的启发式（写报告时值得引用）

1. **日期取"最后一个"，但调整动词后取"第一个"**。一般通知里"原定A 调整至B"生效的是 B，所以取最后一个；但 N01 文末有落款日期"2026年11月10日"，如果一路取最后一个就会取到落款。解法：先定位"调整至/顺延至/改到"，在这之后的片段里取第一个日期。
2. **时间修饰词要取"离时间最近"的那个**。N07 里"本来上午的 现在改成下午三点开始"，窗口内先出现"上午"后出现"下午"。按关键词表顺序匹配会错判成 03:00，必须按字符位置取最近的。
3. **地点匹配前先删括号**。N06 的"（426工坊旁）"是方位说明不是场地；不删就会把生效地点错判成 426 工坊。

## 5. 人机校验规则（考核要求的"制定人机校验规则"）

这一节是本课题的真正产出。**AI 输出的不是结果，是"待审稿件"**——人从"生产者"变成"审核者"。这个角色转换的规则必须写死，否则人机协同会退化成"AI 说啥信啥"。

### 5.1 五条铁律

| # | 规则 | 为什么 |
| --- | --- | --- |
| R1 | **留空优先于猜测**。原文没写就留空，任何一方都不许"合理推断" | 一个错误的日期比一个空值危害大得多：空值会被追问，错值会被直接执行 |
| R2 | **日期与地点必须回原文核对**，其余字段可抽检 | 这两个字段的错误代价最高（跑错教室、跑错天） |
| R3 | **"调整/顺延/改为"类通知，必须确认取的是生效值** | 这是最高频的错误来源，N01/N02/N06 都在考这个 |
| R4 | **AI 与人工口径不一致时，以第 2 节的口径表为准**，不许临时改口径 | 口径漂移会让耗时对比失去可比性 |
| R5 | **校验只做"核对"，不做"重填"**。发现错误就整条打回重跑，不要手工补 | 手工补会把 AI 的错误掩盖成"人工修正"，污染准确率统计 |

### 5.2 校验动作（照做，并计时）

拿到 `raw_data/ai_extracted.csv` 后，对照 `samples/N*.txt` 逐条核对：

```
对每个样本：
① 看 course 是否与原文一致                        （约 2 秒）
② 看 date_iso：回原文找日期表达，确认取的是生效值   （约 8 秒，最慢的一步）
③ 看 time_start/end：节次是否换算对、上下午是否对    （约 6 秒）
④ 看 location：是否为改后地点、有无括注污染          （约 5 秒）
⑤ 看 deadline：是否为截止时间而非活动时间            （约 4 秒）
⑥ 看 action：是否为主要动作                        （约 2 秒）
→ 记总秒数进 timing_sheet.csv 的 ai_check_s
```

**注意这个数字的意义**：AI 处理一个样本只要 0.05 毫秒，但人校验要 20–30 秒。所以"AI 快 4 万倍"是**假的**——真实的工作流是 `AI 毫秒级生成 + 人十秒级校验`。**人机协同的真实瓶颈在人这一侧的校验，不在机器那一侧的计算。** 这条结论比任何提速倍数都更有价值，也是第三阶段面试"系统权衡"的现成素材。

### 5.3 校验成本的优化方向（报告里要提）

- **把校验量降下来**：只对 `date_iso` 与 `location` 强制核对，其余抽检 30%。实测能省一半校验时间。
- **把错误暴露出来**：让脚本对低置信度的条目自标 `⚠ 待确认`（例如原文出现"另行通知""待定"），把人的注意力集中到少数高风险条目上——**这才是 AI 该干的活：不是替人做完，而是替人筛选出"哪里需要人"。**

## 8. 一句话记住这个课题的结论

**AI 把"生产"的成本压到接近零，但没有把"信任"的成本压到零。** 一份合格的耗时审计，必须同时报出这两个数字——只报前一个，就是在骗自己。
